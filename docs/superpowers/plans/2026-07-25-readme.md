# Project README Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a Chinese root README that lets a new user start a design delivery package and gives maintainers an accurate map of the runtime, contracts, tests, and extension points.

**Architecture:** Create one root `README.md` organized by progressive disclosure: project value and quick start first, end-to-end workflow second, maintainer reference last. Treat current scripts, `package.json`, schemas, and Skills as the source of truth; link to the detailed system specification instead of duplicating it.

**Tech Stack:** Markdown, Node.js 18+, npm, ECMAScript modules, Playwright, axe-core, YAML/JSON schemas

### Task 1: Write the user-facing README

**Files:**

- Create: `README.md`
- Reference: `package.json`
- Reference: `skills/design-director/SKILL.md`

- [ ] **Step 1: Add project positioning and capabilities**

Start `README.md` with the project name and a concise Chinese description. State these facts explicitly:

- This is a design Agent runtime for Codex or Claude, not a production frontend framework.
- It converts product requirements into clickable, responsive, high-fidelity HTML prototypes and an auditable delivery package.
- Its main components are one Design Director, five flow Skills, two read-only reviewers, a versioned evidence library, and executable quality gates.

- [ ] **Step 2: Add an exact quick-start path**

Use this command sequence and explain that `outputs/demo` is replaceable:

```bash
npm install
npm run check
npm run env:check
npm run init -- \
  --package outputs/demo \
  --name "示例项目" \
  --mode professional \
  --task-type new_design \
  --platforms web,mobile_web \
  --primary-user "需要完成核心任务的目标用户" \
  --industry general
```

After initialization, show these two checks:

```bash
npm run validate:context -- outputs/demo/context.yaml
npm run accept -- --package outputs/demo
```

Explain that a newly initialized empty package cannot pass final acceptance until all workflow artifacts and reviews exist.

- [ ] **Step 3: Document the end-to-end workflow**

Describe this sequence without implying that npm scripts automatically create creative artifacts:

```text
intake -> research -> ux -> visual -> prototype -> review -> delivered
```

Cover professional mode's requirements, flows, and direction confirmation gates. State that quick mode reduces confirmation rounds but retains hard accessibility, browser, evidence, and audit checks.

- [ ] **Step 4: Add command and delivery-package references**

Document every script in `package.json`, grouping them as system validation, task state, prototype checks, review, and final acceptance. Include commands that have direct Node entrypoints but no npm alias, especially:

```bash
node scripts/director-advance.mjs --package <目录> --stage <阶段>
node scripts/snapshot.mjs --package <目录> --version <版本>
node scripts/record-findings.mjs --package <目录> --version <版本> --in <findings.yaml>
```

Show the delivery package's key files: `context.yaml`, `brief.md`, `flows.md`, `design-tokens.json`, `decisions.md`, `prototype/`, and `audit/`.

- [ ] **Step 5: Add maintainer documentation**

Explain the responsibilities of `skills/`, `scripts/`, `evidence/`, schemas, fixtures, and native checklists. Document these invariants:

- `context.yaml` is the single source of truth and is updated through Director-controlled scripts.
- Internal Skill references use canonical snake_case IDs from `skills/registry.yaml`.
- Skill patches are checked against read/write manifests and the merged context schema.
- Reviews bind to immutable artifact snapshots and the current artifact version.
- Any changed prototype after review requires a new version, screenshots, snapshot, and reviews.

- [ ] **Step 6: Add platform boundaries and links**

State that Web and responsive mobile Web have the complete browser validation path. For iOS, Android, and WeChat Mini Program outputs, HTML can validate information architecture, visual hierarchy, content, states, and some accessibility properties, while native gestures, system controls, safe areas, and runtime behavior require the provided manual checklist or real-device validation.

Link to the system design, context schema, findings schema, Skill manifests, Skill registry, and native checklist directory. Do not add badges, license claims, CI status, or release promises that are not present in the repository.

### Task 2: Verify README accuracy and repository health

**Files:**

- Verify: `README.md`
- Verify: all relative Markdown link targets referenced by `README.md`

- [ ] **Step 1: Check Markdown formatting and relative links**

Run:

```bash
git diff --check
node --input-type=module -e '
  import fs from "node:fs";
  const text = fs.readFileSync("README.md", "utf8");
  const links = [...text.matchAll(/\[[^\]]+\]\((?!https?:|#)([^)]+)\)/g)].map((m) => m[1].split("#")[0]);
  const missing = [...new Set(links.filter(Boolean))].filter((path) => !fs.existsSync(path));
  if (missing.length) { console.error(missing.join("\n")); process.exit(1); }
  console.log(`README relative links OK (${new Set(links).size})`);
'
```

Expected: `git diff --check` exits `0`; the link checker prints `README relative links OK (...)` and exits `0`.
